# Website scraper and run reporting fixes — September 28, 2026

## Causes

- Tourism PG sometimes returned HTTP 403 for the random Windows/Firefox 89
  identity used by the Chromium browser pool. Two live checks reproduced 403
  for that identity and 200 with a calendar for a Chrome identity. The original
  run did not record HTTP status; it exhausted three attempts waiting for a
  calendar element on the returned page.
- PG Pride rendered its events, but GoDaddy background requests prevented
  `networkidle`, exhausting three 45-second navigation attempts. Its responsive
  date/title markup also did not match the former text-scanning heuristics.
- The worker wrote inserts + updates into `eventsFound`. PGPL found 41 events,
  but all were unchanged, so the UI showed 0. Its page counter only included
  the initial navigation, not the eight listing and 41 detail requests.
- Runs use their enqueue timestamp as `startedAt`. The old duration included
  time in the queue and between attempts without explaining that distinction.
- Exceptions caught by the outer job handler were only logged to the worker
  console. The details dialog also read the retired `errorsJsonb` field instead
  of Convex's `errors` field, and did not refresh its run status while logs polled.

## Changes

- Browser identity now matches the actual Chromium engine/version.
- Tourism, Pride and PGPL wait for DOM content instead of network idle and check
  HTTP response status. A blocked request reports its status and URL directly.
- Pride discovers the GoDaddy calendar feed through the page's own response.
  It reads every returned event, including events behind “More Events,” with
  explicit years, end times and timezone offsets. Missing/malformed/failed feeds
  cause an error instead of a false empty success.
- Tourism uses the calendar occurrence date when a detail page lacks a date;
  it never substitutes the scrape date. Invalid calendar dates are rejected.
- PGPL counts listing and detail fetches. Tourism/PGPL count page failures so
  degraded results are marked partial rather than unconditionally successful.
- Website runs persist found/new/updated/unchanged/failed counts plus per-attempt
  timing. Failed attempts preserve page counts; repeated reporting is idempotent.
- Updates to raw event fields or occurrences now count as updates even when
  the series description/title has not changed.
- Failure logs include the attempt number and whether a retry remains. Run logs
  are sequenced and flushed before the worker releases its page.
- Jobs send a heartbeat every 30 seconds; reclaim checks the last update instead
  of assuming every crawl over five minutes has stalled.
- Run history distinguishes total elapsed, active time and waiting time. Details
  refresh during a queued/running run and display current and legacy error fields.
  Historical website counts are labelled new/updated; historical counts/timings
  were not rewritten. Unchanged events remain in the existing catalogue.
